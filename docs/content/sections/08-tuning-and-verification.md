### 8.1 参数清单与语义

系统的全部可调参数集中在管理器的属性面板中，分为「拼图」与「检测」两类。下表的默认值与取值范围取自实现。

<p class="caption">表 8-1 参数默认值、取值范围与调整后果</p>

| 参数 | 默认值 | 取值范围 | 语义 | 调大的后果 | 调小的后果 |
|------|--------|----------|------|------------|------------|
| CameraHeightOffset | 160 | ≥ 0 | 标定原点相对管理器的高度 | 标定点抬高，标定方向更俯视 | 标定点降低，方向更平视 |
| DotProductThreshold | 0.996 | 0.9 – 1.0 | 单碎片方向一致性的余弦下限 | 判定变松，容差角度变大 | 判定变严，容易无法触发 |
| ViewAngleThreshold | 0.996 | 0.9 – 1.0 | 相机朝向与图案中心方向一致性的余弦下限 | 允许更偏的朝向 | 要求朝向更精确 |
| DistanceTolerance | 50 | ≥ 0 | 单碎片距离允许的绝对偏差（世界单位） | 允许前后站位偏差更大 | 站位要求更精确 |
| RequiredPassRate | 0.8 | 0 – 1 | 通过判定的碎片比例下限 | 允许个别碎片不达标 | 要求全部碎片达标 |
| HoldDuration | 1.5 | ≥ 0 | 保持对齐所需时间（秒） | 需要更长时间保持，容错更高 | 更快触发，容易误触发 |
| DetectionInterval | 0.1 | ≥ 0.05 | 检测周期（秒） | 检测更省，反馈更迟钝 | 反馈更灵敏，开销更大 |
| GlowParameterName | GlowIntensity | — | 驱动自发光的标量参数名 | — | 置空则跳过发光控制 |

### 8.2 阈值与角度的换算

方向判据使用余弦而非角度，原因有两点：点积的结果本身就是余弦，无需再做反三角函数；且余弦在接近 0° 处变化平缓，天然形成「越靠近正确视角越宽容」的容差曲线，对操作手感有利。

<p class="caption">表 8-2 余弦阈值与等效角度容差</p>

| 阈值 | 等效角度 | 相对默认值的严格程度 |
|------|----------|----------------------|
| 0.999 | 2.6° | 更严格（约一半容差） |
| 0.996 | 5.1° | 默认 |
| 0.99 | 8.1° | 约 1.6 倍容差 |
| 0.98 | 11.5° | 约 2.2 倍容差 |
| 0.95 | 18.2° | 约 3.6 倍容差 |
| 0.90 | 25.8° | 取值范围下限，判定极松 |

需要注意，方向判据的容差并不等价于「图案在屏幕上偏移多少像素」：同样 5° 的朝向偏差，在近距离碎片上造成的屏幕位移明显大于远距离碎片。因此阈值应按场景尺度试调，而不是照搬默认值。

### 8.3 两类失效模式与参数取舍

**失效模式一：无法触发。** 表现为玩家自认为已站在正确位置，进度条却始终为零。其机制是至少一个判据未达标，常见来源有三：

- 相机高度与标定原点不匹配：角色相机高度随姿态（站立、下蹲）变化，而标定原点在场景中固定；
- 碎片在标定之后被移动，标定数据失效；
- 容差过严：`DistanceTolerance` 偏小或 `DotProductThreshold` 偏高。

**失效模式二：误触发。** 表现为玩家站在明显不正确的位置也能触发，或触发时图案并未真正拼合。其机制是判据过于宽松，常见来源有二：

- `RequiredPassRate` 过低，少量碎片达标即通过；
- 缺少朝向约束：仅用位置判据时，玩家在正确位置附近转身仍可触发。

两类失效模式是同一组参数的两端。工程做法是先固定 `HoldDuration` 与 `DetectionInterval`，再依次收紧方向阈值、距离容差与通过率，每步都用调试可视化确认判定边界与预期一致。

### 8.4 调试手段

系统内置两类互补的调试输出。

**其一，运行期几何可视化。** 标定完成后绘制的调试图元包含：青色球体标记标定原点、橙色球体标记各碎片位置、黄色连线连接原点与碎片（即标定时记录的视线方向）。

<p class="caption">代码 8-1 标定结果的可视化</p>

```cpp
void APerspectivePuzzleManager::DrawDebugCalibration(float Duration) const
{
    if (CalibratedData.Num() == 0) return;

    // 标定原点
    DrawDebugSphere(GetWorld(), CalibratedOrigin, 20.0f, 12, FColor::Cyan, false, Duration);

    for (const auto& Point : CalibratedData)
    {
        DrawDebugSphere(GetWorld(), Point.WorldLocation, 15.0f, 8, FColor::Orange, false, Duration);
        DrawDebugLine(GetWorld(), CalibratedOrigin, Point.WorldLocation, FColor::Yellow, false, Duration);
    }
}
```

此外，每次检测还会绘制两条短射线：红色表示玩家当前视线，绿色表示标定时的目标视线方向。两条射线在正确视角下重合，其夹角即为朝向误差。

**其二，分级日志。** 检测过程输出三类信息：相机位置与标定原点的距离、每次检测的汇总（通过碎片数、通过率、朝向点积、是否对齐），以及未通过碎片的具体偏差。

<p class="caption">代码 8-2 定位「哪一条判据没有通过」</p>

```cpp
UE_LOG(LogTemp, Log, TEXT("CheckPuzzle: Pass=%d/%d Rate=%.2f ViewDot=%.4f Aligned=%s"),
    PassCount, CalibratedData.Num(), Rate, ViewDot, bAlignedNow ? TEXT("true") : TEXT("false"));

// 未通过的碎片单独打印，便于区分方向不符与距离不符
UE_LOG(LogTemp, Log, TEXT("  Mismatch: Dot=%.4f(need>=%.4f) DistDiff=%.1f(need<=%.1f)"),
    Dot, DotProductThreshold, DistDiff, DistanceTolerance);
```

两类输出的分工是：可视化回答「差多少」，日志回答「哪一条不满足」。出现无法触发的现象时，先看日志判断是方向、距离还是朝向判据失败，再用可视化确认几何关系是否正确。

### 8.5 标定一致性验证流程

标定数据是运行期判定的唯一依据，其正确性只能通过「站在标定位置看是否达标」来验证。建议流程如下：

1. 完成碎片摆放，确认各碎片位于不同的纵深位置；
2. 触发一次标定，检查日志中的记录条数与碎片数量一致；
3. 打开调试可视化，确认青色球体位于预期高度（管理器位置加相机高度偏移），橙色球体与碎片一一对应；
4. 将相机移动到标定点，观察两条调试射线是否重合、通过率是否为 1.0、朝向点积是否接近 1.0；
5. 若通过率不足 1.0，按日志逐条修正碎片位置或容差；
6. 保持正确视角超过保持时间，确认事件被触发、进度走满、碎片发光归一。

移动任一碎片后必须重新标定：`TargetDirection` 与 `TargetDistance` 均以标定原点为参考计算，碎片移动即失效。

### 8.6 性能与数值考量

- **计算量**：每次检测对 N 个碎片各做一次向量减法、取模、归一化与点积，复杂度 O(N)；默认 0.1 秒的周期使该开销与帧率解耦，并与 N 呈线性关系。
- **使用余弦而非角度**：避免反三角函数，同时避免浮点相等比较。
- **比较使用下界**：方向判据为「点积 ≥ 阈值」，距离判据为「偏差 ≤ 容差」，边界值即通过，语义清晰。
- **归一化的安全处理**：向量归一化使用 `GetSafeNormal()`，在向量长度为零时返回零向量而不产生 NaN。
- **定时器与状态**：检测在定时器回调中执行，`bIsSolved` 为真时提前返回并清除定时器，避免解谜完成后继续计算。

### 8.7 小结

参数标定的本质是在「宁可触发不了」与「宁可误触发」之间选择工作点：前者牺牲手感，后者牺牲谜题的可信度。可行做法是先按默认值运行、用可视化确认几何关系无误，再依据失效模式的类型定向调整单一参数，并在每次调整后重复 8.5 的验证流程。
