透视图案拼接谜题：基于方向—距离联合判据的视角检测系统

虚幻引擎 5 中的系统架构、标定方法、运行期检测与视觉反馈实现

Particle Light·2026 年 8 月·技术报告 · Technical Report

摘要

「透视图案拼接」是一类依赖观察视角的空间谜题：一个完整图案被拆成若干碎片，分别附着在场景中纵深不同的物体表面，只有观察者站在特定位置并以特定朝向观察时，碎片才会在视野中拼合成完整图案。

本文给出该谜题在虚幻引擎 5 中的一个完整实现，核心是一套方向—距离联合判据：标定阶段记录每个碎片相对标定原点的单位方向与直线距离；运行阶段以玩家相机为参考点，重复计算同一组方向与距离并逐项比对，同时用图案中心方向约束观察朝向，最后以通过率与保持时间决定谜题是否解开。

本文的主要内容包括：（1）把「正确视角」形式化为可计算的数据，并说明为何选择方向与距离而非绝对坐标；（2）给出检测判据的完整定义、阈值语义（阈值以余弦形式表达角度容差）与状态机设计；（3）给出碎片图案在材质层的切分方法与运行期发光反馈的实现（动态材质实例驱动自发光参数）；（4）整理虚幻引擎反射系统的编译约束与常见故障的定位方法；（5）给出参数标定的实验方法与调试手段。

文中所有实现细节均取自实际工程的源码，参数默认值与取值范围与源码一致；关键判据均给出几何解释与失效条件分析。

关键词：虚幻引擎 5；视角检测；点积；方向—距离判据；标定；动态材质实例；贴花；自发光

#1引言

1.1 问题背景

在若干动作与解谜类游戏中，出现过一类共同的视觉机关：一个完整图案被拆散到场景中不同物体上，玩家只有在特定位置、以特定朝向观察时，各碎片才会在视野中拼合成完整图案并触发机关。此类机关的实现难点并不在图案本身，而在于如何判定玩家当前是否处在正确的观察视角。

这个判定问题有三个直观但并不可靠的替代做法：一是放置触发器体积，但体积只能约束位置、无法约束朝向，且体积的轴向与玩家视线无关；二是比较玩家位置与某个目标点的欧氏距离，同样无法约束朝向；三是做屏幕空间的图案识别，比较渲染结果与模板图，其鲁棒性受分辨率、光照与遮挡影响，成本也远高于收益。

本文给出的方案把「正确视角」拆成两组可计算的量：

  • 位置相关量：从标定原点到每个碎片的方向与距离；
  • 朝向相关量：从标定原点到图案中心的方向。

两者都以单位向量与标量的形式保存；运行时只需重复同样的计算并与标定值比对，即可得到当前视角与正确视角的接近程度。该方案不依赖屏幕空间信息，不受渲染分辨率与光照影响，计算量为每个碎片一次减法、一次取模、一次归一化与一次点积。

1.2 问题的形式化描述

设场景中有 N 个碎片（N ≥ 1），第 i 个碎片的世界坐标为 pi。设计者在场景中选定一个观察位置 o（位于相机高度）与一个朝向 f，使所有碎片在该视角下拼合为完整图案。

判定目标是：给定当前相机位置 c 与朝向 fc，判断 (c, fc) 是否落在 (o, f) 的一个可接受邻域内，并输出连续的对齐程度，用于驱动视觉反馈。

该描述同时说明了两件事：其一，判定必须同时覆盖位置与朝向；其二，输出应是连续量而非布尔量，因为谜题通常需要一个“逐渐对齐”的反馈过程。

#2检测方案的比较与选型

2.1 视觉前提：视差与透视

碎片能在特定视角拼合，依赖两个几何事实。

其一，视差随观察位置变化。 两个位于不同纵深的物体，在相机移动时其投影的相对位置会发生相对位移。设碎片 A、B 分别位于深度 dA、dB（dA ≠ dB），相机横向移动 Δ 时，两者在成像平面上的位移差约为 Δ·(1/dA − 1/dB)。因此碎片一旦摆放完毕，能拼合的位置集合就被唯一确定——这正是谜题只在一个特定位置成立的原因。

其二，投影关系随观察方向变化。 相机朝向决定成像平面的姿态：朝向偏离时，同一组碎片在屏幕上的相对位置随之变化，图案不再吻合。因此“位置正确”并不蕴含“朝向正确”。

上述两点共同说明：判定量必须同时对位置与朝向敏感，且敏感度应随偏离程度单调变化，才能提供渐进反馈。

2.2 三类候选方案

表 2-1 三类检测方案的比较

方案判定依据能否约束朝向与几何一致主要代价
A. 触发器体积 / 距离比较玩家位置与目标点的距离否弱（体积轴向与视线无关）低
B. 屏幕空间图案识别渲染结果与模板图的相似度是强，但代价高高（渲染回读、图像比对）
C. 方向—距离联合判据相机到各碎片的方向与距离，加上到图案中心的方向是强低（每碎片常数次向量运算）

方案 A 的问题不在于精度，而在于信息缺失：位置正确而朝向错误时仍会判定成功，玩家可以背对图案触发机关。方案 B 在几何上最忠实，但需要读取渲染结果并与模板比对，其稳定性受分辨率、抗锯齿、光照与遮挡影响，且每帧的额外开销与分辨率成正比。方案 C 用几条向量运算表达了与方案 B 相同的几何约束：只要相机位置与朝向正确，碎片方向与距离必然与标定值一致；反之，方向或距离任一项不符即说明视角偏离。

方案 C 的代价是需要在场景中显式指定碎片集合，并在设计阶段完成一次标定；这一代价换取的是判定完全确定、可解释、可调参，且不依赖渲染管线。

2.3 选型结论

本文采用方案 C，并将其组织为三个层次：

  1. 标定层：把设计者选定的观察位置与朝向，转换为每个碎片的方向与距离，以及图案中心方向。
  2. 判定层：运行期重复同一组计算，按阈值逐项比对，得到通过率与朝向匹配结果。
  3. 状态层：以通过率与朝向的联合条件驱动一个带保持时间的状态机，输出对齐事件与进度。

需要强调的是，方案 C 判定的是视角而非成像结果：它不检查碎片是否真的在屏幕上拼合，而是检查“相机是否处在能让它们拼合的那个位置和朝向”。二者的差别在遮挡场景下会体现出来——若某个碎片被中间物体挡住，方案 C 仍会判定对齐。第 5 章给出的视线判据只能约束朝向，不能替代遮挡检测；这一点在第 9 章作为局限列出。

2.4 与其他要素的关系

检测只是谜题的一半，另一半是图案的呈现。两者的接口位于材质参数：

  • 检测层输出一个 [0, 1] 的对齐进度；
  • 呈现层把该进度写入碎片的材质标量参数，驱动自发光强度。

这种分工使得检测逻辑与视觉表现相互独立：更换图案、更换承载方式（贴画或网格体）都不影响检测，反之亦然。第 6 章将展开呈现层的实现。

#3系统架构与运行时对象模型

透视拼接谜题的判定目标只有一句话：玩家是否站在标定过的那个视点上，并朝着标定过的方向观察。这句话里没有任何“碎片自身的行为”，因此系统不需要为每个碎片写逻辑，只需要一个能在全局视角下比对“当前相机状态”与“标定状态”的宿主对象。

这一约束直接决定了整体形态：一个管理器 Actor 独占全部逻辑与状态，碎片只作为被引用的场景对象，玩家相机是唯一的运行时输入源。本章说明该划分的设计动机、两条数据链路，以及对外暴露的接口与生命周期。文中引用的源码片段保留原始标识符与注释，缩进统一按四空格归一。

3.1 设计目标与约束

系统需要同时满足四组约束，它们共同排除了若干看似更简单的实现方式。

其一：碎片数量可变。 一个图案可以被拆成 2 块、4 块或 9 块。任何形如“遍历两个固定对象”的写法都会在拆分数变化时失效，因此碎片必须以列表形式登记，且所有判定循环、通过率计算、发光遍历都只能以列表长度为准，不能出现与具体数量绑定的常数。

其二：碎片摆放自由。 碎片在场景中的位置由人工摆放决定，三维位置、朝向、承载物（柱子、墙面、悬浮平面）都不受系统约束。系统只能读取碎片的世界坐标，不能对摆放提出格式要求。

其三：可重新标定。 “正确视角”不是预先写死在数据里的常量，而是在编辑期由人工把碎片摆好之后，由系统现场测量并固化的一组数据；摆放调整后可以重新执行同一次测量，覆盖旧数据。这意味着标定过程必须是幂等的、可重复调用的，且不能依赖于任何一次性的初始化路径。

其四：判定是全局的，而表现是局部的。 是否“拼合成功”取决于全部碎片的整体状态（通过比例），以及玩家视线是否落在图案整体上；而“成功后做什么”（开门、播放动画、显示提示）属于表现层，与判定算法无关，且改动频率远高于算法。两者必须解耦，否则每次调整表现都需要重新编译 C++。

3.2 角色划分：管理器、碎片、玩家相机

系统由三类参与者构成，彼此之间是单向引用关系。

3.3 为什么把逻辑集中在管理器

把检测分散到各个碎片上（每个碎片自己判断“是否被正确观察”）在直觉上更“面向对象”，但在本问题里会立即遇到三处无法局部化的依赖。

全局通过率无法由局部决定。 判定条件之一是“通过检测的碎片占比不低于 RequiredPassRate”。单个碎片只能知道自己是否通过，无从知道总数与通过数。若把计数责任上移，碎片上的判定逻辑就只剩“方向点积与距离差”这一条，形同虚设。

视线检测的参考点是全局量。 视线判定使用的目标方向由“所有碎片位置的几何中心”决定：

代码 3-1 图案中心的定义与计算（节选自 Calibrate 实现）

    FVector CenterAccum = FVector::ZeroVector;
    int32 Count = 0;

    for (AActor* Actor : FragmentActors)
    {
        if (!Actor) continue;

        FCalibratedMarkPoint Point;
        Point.FragmentActor = Actor;
        Point.WorldLocation = Actor->GetActorLocation();

        FVector Dir = Point.WorldLocation - CalibratedOrigin;
        Point.TargetDistance = Dir.Size();
        Point.TargetDirection = Dir.GetSafeNormal();

        CalibratedData.Add(Point);
        CenterAccum += Point.WorldLocation;
        Count++;
    }

    // 图案中心 = 所有碎片的几何中心，作为视线检测的参考点
    CalibratedViewTarget = (Count > 0) ? CenterAccum / Count : CalibratedOrigin;

这个中心是全部碎片位置的算术平均，任何一个碎片都无法单独计算；它也不等于任何一个碎片的位置。把视线检测放到碎片上，就必须把中心作为额外数据下发，等于把耦合显式化而没有消除。

状态必须是单点。 bIsSolved、SolveProgress、HoldTimer、bWasAligned 描述的是“整个谜题”的状态。若每个碎片各持一份，就会出现“碎片的成功标记不一致”这类无法收敛的问题；事件派发（OnViewAligned / OnViewLost / OnPuzzleSolved）也必须是唯一的边沿触发点，否则一次对齐会触发 N 次事件。

此外还有两条工程上的收益：检测只需要一个定时器句柄（DetectionTimerHandle），而不是每个碎片一个；判定逻辑集中在约百行的单个函数内，便于整体替换判定策略。

需要说明的是，“集中”并不意味着管理器侵入碎片的行为。它对碎片的接触只有三类：读取世界坐标、为碎片组件创建动态材质实例、向该实例写入标量参数。碎片的位置、旋转与缩放始终由人工维护，管理器从不修改任何变换。

3.4 数据流：标定期与运行期

系统的数据流分为两条彼此独立的链路，分别在不同的时间尺度上运行。

标定期链路把“场景事实”转换成“判定依据”。输入是登记在 FragmentActors 中的碎片列表与管理器自身的位置；输出是两类标定数据：逐碎片的 CalibratedData，以及供视线判定使用的 CalibratedViewTarget；标定视点本身（CalibratedOrigin）也在这一步确定。

每个碎片的数据被组织为一个 USTRUCT，把“哪个 Actor、标定时在哪、相对标定点的方向与距离”聚合在同一结构内，避免使用多个平行数组而在增删碎片时错位：

选择“方向 + 距离”而不是“相对坐标”，是因为运行期的比对对象正好是这两个量：方向用点积比较（对角度敏感），距离用绝对差比较（对尺度敏感）。若存相对坐标，检测时仍需先算出长度与单位向量，等于把同一份计算做了两遍。

运行期链路以固定的时间间隔采样玩家相机，把“当前相机状态”与标定数据比对，产生状态迁移与对外消息。

三个分组的设计意图各不相同。

参数（EditAnywhere）承担调参职责。 方向容差、距离容差、通过比例、保持时长都属于手感参数，需要在运行时反复试凑。把它们暴露为可编辑属性，调参过程就不需要重新编译；ClampMin / ClampMax 元数据同时起到范围保护作用——例如方向容差被约束在 [0.9, 1.0]，而余弦值只有落在该区间才对应“小角度偏差”这一物理含义。

状态（BlueprintReadOnly）只读不写。 状态由判定逻辑单方面维护，若同时开放写权限，蓝图侧的任何误写都会让状态机与判定结果脱节；只读暴露既满足了表现层读取进度的需求，又保持了状态的单一来源。

表现（BlueprintImplementableEvent）只在 C++ 中声明。 这四个函数没有 C++ 实现体，蓝图侧以事件节点形式出现，实现内容完全由表现层决定。这样划分的收益是双向的：C++ 侧只需保证“在正确的时机调用一次”，不必知道成功后要开门还是播放音效；表现侧则可以在不触碰判定算法的前提下增删逻辑，且不需要重新编译 C++ 模块。

值得注意的是事件语义被刻意设计为两种形态。OnViewAligned / OnViewLost 属于边沿触发：由 bWasAligned 保存上一次采样结果，只有状态发生翻转时才各触发一次，适合播放一次性的音效或动画。OnProgressUpdated 则属于电平刷新：它在对齐期间随每次采样派发，携带连续变化的进度值，适合驱动进度条或渐强效果。

两者在“失去对齐”这一情形下的分工需要特别留意：失焦分支把 HoldTimer 与 SolveProgress 清零，但不派发 OnProgressUpdated，归零通知完全由 OnViewLost 承担。表现层若只在 OnProgressUpdated 中更新进度显示，就会在失焦瞬间停留在上一次的进度值上；正确做法是在 OnViewLost 中同步复位显示。

成功分支在置位 bIsSolved 之后又显式派发了一次 OnProgressUpdated(1.0f)。由于该次采样的进度值经 Clamp 后已经是 1.0，这次派发在数值上是重复的；它的实际作用是把“成功即进度为 1”这一契约写在成功路径上，而不是依赖钳制的边界行为。

3.6 生命周期

Actor 的生命周期钩子只有两个被使用：构造函数负责建立组件结构，BeginPlay 负责按固定顺序完成一次性初始化。

代码 3-3 构造函数与 BeginPlay 的初始化顺序（节选，中间的空 Tick 实现已省略）

APerspectivePuzzleManager::APerspectivePuzzleManager()
{
    PrimaryActorTick.bCanEverTick = false;
    RootComponent = CreateDefaultSubobject<UArrowComponent>(TEXT("Root"));
}

void APerspectivePuzzleManager::BeginPlay()
{
    Super::BeginPlay();

    Calibrate();
    CacheFragmentMaterials();
    ResetPuzzle();
    DrawDebugCalibration(100000.0f); // 调试：运行时持续显示目标位置和碎片位置
}

构造函数只做两件事。 其一是关闭逐帧 Tick（bCanEverTick = false）：检测由定时器按 DetectionInterval 驱动，逐帧回调（约 16 ms 一次）既无必要也浪费性能，关闭后 Tick 的实现体保持为空且不会被调用。其二是指定根组件。根组件是 Actor 组件树的锚点，RootComponent 必须被赋值，否则组件无法参与变换层级。此处选择 UArrowComponent 而非更“通用”的 USceneComponent，原因是箭头在编辑器中自带方向可视化：管理器在关卡里同时表达“标定位置”和“观察朝向”两个信息，箭头使两者都能被肉眼确认，摆放阶段不必依赖调试绘制。

BeginPlay 的四步顺序不可交换。 Calibrate() 必须先于 CacheFragmentMaterials()，因为标定可能因空指针等原因跳过部分碎片，而材质缓存遍历的是同一份 FragmentActors 列表，两者共享同一轮人工登记结果；若先建材质再标定，一旦中途调整了列表就会出现索引错位。ResetPuzzle() 必须在标定之后，因为它除了复位状态，还负责启动检测定时器——定时器的第一次回调会立即使用标定数据，若数据尚未建立，首次采样会因 CalibratedData.Num() == 0 直接返回。最后的 DrawDebugCalibration(100000.0f) 传入一个极大的持续时长，使调试几何体在整个运行期间保持可见，便于在游玩过程中确认标定位置是否与预期一致。

重置与初始化共用同一条路径。 ResetPuzzle() 同时承担“首次启动”与“重复调用”两种语义：它先清除既有的定时器句柄再重新注册，因此重复调用不会叠加多个定时器；状态字段被显式复位为初值，bIsSolved 也随之清除。这一设计使系统天然支持“谜题重新开始”，代价是解谜成功后若再次调用重置会重新开启检测，该行为是否符合预期取决于使用场景，需要在关卡逻辑中明确约定。

3.7 小结

  • 判定目标的全局性决定了架构形态：碎片只提供世界坐标与材质，相机只提供视点采样，全部状态与判定逻辑集中在单一的管理器 Actor 中。
  • 碎片数量可变这一约束贯穿实现：所有循环、通过率、材质遍历都以列表长度为准，判定结果由“通过比例”而非“全部通过”给出，使拆分数量变化时无需修改任何常数。
  • 数据被明确划分为两条链路：标定期把场景事实固化为 CalibratedData、CalibratedOrigin 与 CalibratedViewTarget；运行期只做采样比对，产生状态迁移与对外消息。
  • 接口按职责三分：可编辑属性承担调参，只读属性暴露状态，BlueprintImplementableEvent 把表现层完全外置，使判定算法与表现形式可以独立演进。
  • 生命周期上关闭了逐帧 Tick，改由固定间隔的定时器驱动；BeginPlay 中标定、材质缓存、重置与调试绘制四步的先后顺序由数据依赖决定，不可交换。

#4标定：正确视角的确定与数据表示

透视拼接谜题把一张图案拆成若干碎片，分别贴在不同深度的物体表面。只有当观察者处在某一个特定位置、朝某一个特定方向看去时，碎片才会在视野里拼合成完整图案。这意味着系统的第一项任务不是“检测”，而是把一个几何事实固定下来：设计者认定的那个正确视角，究竟对应哪些可计算的量。这个过程称为标定（calibration）。

标定只在场景确定后执行一次，产物是一份紧凑的数据表；运行期检测的全部工作，就是把实时相机状态与这份数据表逐项比对。因此标定的数据表示直接决定了检测判据的表达能力——少存一个量，就会有一整类错误姿势无法被排除。

4.1 标定的目标

标定需要回答两个问题：

  1. 观察者应当站在哪里——一个世界坐标，称为标定原点（CalibratedOrigin）；
  2. 从这个位置看出去，各碎片呈现为何种几何关系——为每个碎片保存一个方向与一个距离。

值得强调的是标定的输入：它读取的是碎片在场景中的摆放位置，而不是图案图像本身。碎片是被人为摆放到“在正确视角下恰好拼合”的位置上的，因此“正确视角”与“标定时所采样的那组几何关系”在系统中等价。这一等价关系带来两个直接后果：

  • 判定基准完全由场景摆放决定，调整图案的视觉拼接效果不需要改动检测代码；
  • 一旦碎片位置改变，旧标定立即失效，且失效是静默的——检测不会报错，只会永远不通过。

4.2 标定原点：为什么在 Manager 位置之上再加偏移

标定原点并不取 Manager Actor 自身的坐标，而是在其基础上做一次垂直抬升：

代码 4-1 标定原点的计算（节选自 `PerspectivePuzzleManager.cpp`）

	CalibratedOrigin = GetActorLocation() + FVector(0, 0, CameraHeightOffset);

各量的含义如下：

Origin = ManagerLocation + (0, 0, h)，h = CameraHeightOffset

其中 CameraHeightOffset 的默认值是 160.0（单位与 UE 的世界单位一致，即厘米），并带有 meta = (ClampMin = 0.0f) 的下限约束。

为什么要拆成两个量。 把 Manager 放在地面上摆放，符合关卡编辑的直觉：地面是天然的参考平面，坐标水平方向的 X/Y 可以直接对着地砖网格拖拽，Z 保持在 0 便于判断“人站在哪一格”。真正需要精确控制的只是高度，于是把高度单独抽成一个可调标量。若把原点直接绑在 Actor 上，则需要把 Actor 悬空放置到视高，既难以对准地面网格，也让“水平站位”与“观察高度”两个互相独立的意图挤在同一个坐标里。

高度偏移的语义是“玩家视高”。 运行期的位置判据用的是玩家相机位置，因此 CameraHeightOffset 必须等于该角色实际的眼高，而不是一个想当然的经验值。一旦两者不一致，原点就会与相机存在一个固定的垂直偏差，这个偏差会同时污染方向与距离两项判据：相机沿着垂直方向偏离原点后，指向碎片的单位向量会整体倾斜，点积随之下降；同时相机到碎片的距离也会改变。

这种失效有一类特征明显的现象：水平站位完全正确、朝向也正确，但判定始终不通过，且日志中“相机到原点的距离”稳定停在一个非零值上。例如把 Manager 放在 Z=0 的地面、偏移取默认 160，而角色相机实际位于 Z=246 时：

代码 4-2 高度不匹配时的典型日志

水平方向只差约 10 个单位，垂直方向却差了 86 个单位——偏差几乎全部来自高度，足以让方向判据跌出容差。把 CameraHeightOffset 改为 246（即角色真实视高）后，原点与相机重合并恢复通过。这里的结论不是“某个数值错了”，而是：该参数没有可继承的默认值，必须按角色实测。

4.3 单碎片标定量：方向与距离的极坐标分解

每个碎片对应一条标定条目，其数据表示是一个带反射标记的结构体：

为什么存“方向 + 距离”而不是只存位置。 只存位置在原理上也能恢复方向与距离（做减法即可），但把二者显式分解出来会带来两点实质差别。

其一，判据可以直接建立在“相对相机”的量上，无需在每次检测里重复推导基准。更关键的是第二点：方向与距离在几何上互补，各自存在一整类无法分辨的退化情形。

  • 方向对“沿射线的前后位置”完全不敏感。 设标定原点为 $O$、碎片为 $P$，令 $\hat{d} = (P - O)/|P - O|$ 为标定方向。若把相机沿同一条射线前后移动，即 $C = O + t\hat{d}$（$t > 0$），则当前方向

(P − C)/|P − C| = ((1 − t)·(P − O))/|1 − t|·|P − O| = ±d̂

始终与标定方向平行，点积恒为 1。但沿射线前后移动会直接改变观察距离，使其在不同深度上的碎片产生不同比例的缩放，图案因视差而散开。仅靠方向判据，这条射线上的任意位置都会通过。

  • 距离对“绕碎片的横向位置”不敏感。 若相机在以碎片为球心、TargetDistance 为半径的球面上移动，相机到碎片的距离保持不变，但方向已经改变。

两者合起来才构成一个完整的约束：方向锁住“从原点看出去的角位置”，距离锁住“沿该方向的尺度”。这在几何上正是把 $(P - O)$ 做了极坐标分解——一个单位方向加一个半径。检测侧的对偶形式是：

Dot = Ĉ·d̂ ≥ DotProductThreshold，DistDiff = ||C − P| − TargetDistance| ≤ DistanceTolerance

关于反射标记还有一个容易忽略的细节：四个字段中只有 FragmentActor 带有 UPROPERTY 宏，WorldLocation、TargetDirection、TargetDistance 都是普通成员。这意味着后三者不参与引擎的反射与序列化，不会出现在细节面板中，也不能直接被蓝图读写。它们被当作纯运行期数据使用——这是有意的取舍，但也意味着标定结果无法在编辑器里逐项目视检查，只能依赖 4.6 的调试绘制。

4.4 图案中心：视线判据的单一参考点

除逐碎片的条目外，标定还产出第二个量——所有碎片位置的几何中心：

代码 4-4 图案中心的累加与求平均（节选自 `PerspectivePuzzleManager.cpp` 的 `Calibrate()`）

	FVector CenterAccum = FVector::ZeroVector;
	int32 Count = 0;

	for (AActor* Actor : FragmentActors)
	{
		if (!Actor) continue;

		FCalibratedMarkPoint Point;
		Point.FragmentActor = Actor;
		Point.WorldLocation = Actor->GetActorLocation();

		FVector Dir = Point.WorldLocation - CalibratedOrigin;
		Point.TargetDistance = Dir.Size();
		Point.TargetDirection = Dir.GetSafeNormal();

		CalibratedData.Add(Point);
		CenterAccum += Point.WorldLocation;
		Count++;
	}

	// 图案中心 = 所有碎片的几何中心，作为视线检测的参考点
	CalibratedViewTarget = (Count > 0) ? CenterAccum / Count : CalibratedOrigin;

其定义即等权算术平均：

CalibratedViewTarget = (1/N) Σᵢ pᵢ，N 为有效碎片数

为什么不用“各碎片方向的平均”。 一个自然的替代方案是先把每个碎片的单位方向向量求平均，用结果作为视线参考方向。这种做法有三个问题，且第一个是致命的：

  1. 可能退化为零向量。 若两个碎片相对原点近似相反（例如一前一后），单位向量的平均长度趋近于 0；GetSafeNormal() 对零长度向量返回零向量，随后与相机朝向的点积恒为 0，视线判据将永远无法通过。这类失败既不报错也无法通过调参救回。
  2. 丢失“看向何处”的语义。 方向平均把距离完全不同的碎片当作等权样本，得到的既不对应任何碎片，也不对应图案的视觉中心。
  3. 与位置判据的职责重叠。 位置判据已经是“逐碎片比方向”的多路比较；视线判据需要回答的是另一个问题——观察者是否正看着图案整体。几何中心正是拼合后图案的视觉中心，与“看向图案”这一行为直接对应。

由此形成职责分离：位置判据逐碎片比较（多路方向 + 多路距离），视线判据只比较一个方向（原点 → 几何中心）。

需要留意一个退化分支：当 Count 为 0 时，代码把 CalibratedViewTarget 直接取为 CalibratedOrigin。此时“几何中心减原点”是零向量，视线方向无定义，判据恒不通过。实际上 CheckPuzzle() 在 CalibratedData.Num() == 0 时会提前返回，因此该分支属于防御性写法，而不是可运行的正常路径。

4.5 标定流程与调用时机

标定在 BeginPlay() 中与材质缓存、状态重置一起构成初始化序列：

代码 4-5 初始化序列（节选自 `PerspectivePuzzleManager.cpp`）

void APerspectivePuzzleManager::BeginPlay()
{
	Super::BeginPlay();

	Calibrate();
	CacheFragmentMaterials();
	ResetPuzzle();
	DrawDebugCalibration(100000.0f); // 调试：运行时持续显示目标位置和碎片位置
}

四步的顺序不是随意的：

  1. Calibrate() 必须最先。ResetPuzzle() 会开启一个以 DetectionInterval（0.1 秒）为周期的循环定时器，而 CheckPuzzle() 的第一句就是“已解出或标定数据为空则返回”。如果定时器先于标定启动，最初的若干个检测周期会静默地在空数据上返回——功能上无害，但会掩盖“标定失败”这一真实故障。
  2. CacheFragmentMaterials() 在标定之后执行，为每个碎片建立可供运行时改参的动态材质实例；检测通过时写入发光参数的就是这批实例。
  3. ResetPuzzle() 清零状态并启动定时器，从此进入运行期检测。
  4. DrawDebugCalibration(100000.0f) 以约 27.8 小时的存活时间绘制标定图元，等效于常驻显示。

Calibrate() 自身的副作用同样值得注意。它以 CalibratedData.Empty() 开头，因此重复调用是幂等的——先清空再重建，不会累积旧条目。这正是它能够被挂到编辑器按钮上（CallInEditor = "true"）反复执行的前提：改动碎片位置后重新标定，得到的一定是当前场景的完整快照。

标定结束时写入的日志是判断“碎片有没有被正确挂上”的第一手证据：

代码 4-6 标定结果日志（节选自 `PerspectivePuzzleManager.cpp`）

	UE_LOG(LogTemp, Log, TEXT("Calibrate: %d points recorded, view target %s"), CalibratedData.Num(), *CalibratedViewTarget.ToString());

标定条目数少于预期，通常意味着 FragmentActors 数组中有空槽或漏拖。这里存在一处需要留意的容忍度不一致：Calibrate() 用 if (!Actor) continue; 跳过空槽，并且只对有效碎片计数（因此通过率的分子分母始终自洽）；而 CacheFragmentMaterials() 没有任何空指针防护，它直接对数组的每个元素调用 FindComponentByClass。两者对同一份 FragmentActors 的健壮性不同，实践含义是：FragmentActors 中不应保留未赋值的空槽。

4.7 小结与边界

标定的实质是一次性采样：把“正确视角”固化为原点坐标、每碎片的方向与距离、以及图案中心三项产物。运行期不再重新推导任何基准，只做比对。这种设计的代价与收益都很明确：判据简单、稳定、可解释，但基准与场景摆放严格绑定。

表 4-4 标定产物的运行期去向

产物类型运行期使用位置

边界与注意事项：

  1. 改变碎片位置后必须重新标定。 运行期不会读取碎片的实时位置来更新基准，旧标定的失配是静默的。
  2. 标定与运行期必须共享同一套坐标与同一视高。 CameraHeightOffset 与实际相机高度的偏差会同时污染方向与距离两项判据，且无法通过调阈值可靠补偿。
  3. FragmentActors 不应留空槽。 Calibrate() 会跳过空槽而 CacheFragmentMaterials() 不会，两者的健壮性不一致。
  4. 一份标定只对应一个正确视角。 需要多个解法的谜题应使用多个 Manager 实例，各自持有独立的 FragmentActors 与标定结果。
  5. 标定数据不包含朝向信息。 观察者朝向由 CalibratedViewTarget 单独承担，二者缺一不可——这也是位置判据与视线判据必须同时成立的原因。

#5运行期检测：方向—距离联合判据与状态机

标定给出一份静态基准：原点、每个碎片的方向与距离、以及图案中心。运行期的任务是把实时相机状态与这份基准逐项比对，并把“连续多个周期都成立”这一时间维度纳入判定。整个检测由两部分构成：一组空间判据（方向、距离、通过率、视线），以及一个状态机（边沿事件、保持计时、完成与重置）。

5.1 检测的时间模型：定时器轮询而非逐帧 Tick

检测的驱动方式在构造阶段就已确定，其中起决定作用的是这一行：

代码 5-1 关闭 Actor 的逐帧 Tick（节选自 `PerspectivePuzzleManager.cpp`）

	PrimaryActorTick.bCanEverTick = false;

其语义是引擎根本不会把这个 Actor 注册到逐帧更新列表。类中虽然仍有一个 Tick() 覆写，但它只调用 Super::Tick(DeltaTime)，不含任何逻辑——检测与帧循环完全解耦。检测改由循环定时器驱动，在重置时建立：

代码 5-2 循环定时器的建立（节选自 `PerspectivePuzzleManager.cpp` 的 `ResetPuzzle()`）

	GetWorldTimerManager().ClearTimer(DetectionTimerHandle);
	GetWorldTimerManager().SetTimer(DetectionTimerHandle, this, &APerspectivePuzzleManager::CheckPuzzle, DetectionInterval, true);

SetTimer 的最后一个实参 true 表示循环触发，周期为 DetectionInterval（默认 0.1 秒），即 10 Hz 的检测频率。

为什么不用逐帧 Tick。 判据处理的是玩家的空间位置，而人移动的速度在量级上是每帧若干厘米；把采样率从 60 Hz 降到 10 Hz，检测的最坏延迟是 0.1 秒，远低于“玩家察觉到判定没响应”的阈值。反过来，逐帧检测会把同一套“逐碎片求差 + 点积”的计算量放大约 6 倍，而收益为零——判据本身是幂等的纯比较，不存在需要逐帧积分的状态。

这一选择有两个附带语义：其一，计时以检测周期为单位（见 5.6），“持续 1.5 秒”等价于“连续 15 个检测周期都判定为对齐”；其二，定时器仍运行在游戏线程上，受调度粒度约束，极长的单帧同样会推迟回调。

5.2 相机状态的获取

单次检测首先取得玩家视点，并对空指针做保护：

代码 5-3 取玩家控制器与视点（节选自 `PerspectivePuzzleManager.cpp` 的 `CheckPuzzle()`）

	if (bIsSolved || CalibratedData.Num() == 0) return;

	APlayerController* PC = UGameplayStatics::GetPlayerController(GetWorld(), 0);
	if (!PC || !PC->PlayerCameraManager) return;

	FVector CamLoc;
	FRotator CamRot;
	PC->GetPlayerViewPoint(CamLoc, CamRot);
	FVector CamForward = CamRot.Vector();

三个环节各自有明确意图：GetPlayerController(GetWorld(), 0) 取本地玩家 0 号控制器，索引 0 意味着单机单玩家假设，分屏或多玩家场景需要另行扩展；if (!PC || !PC->PlayerCameraManager) return; 是必要的防御，因为 GetPlayerViewPoint 的实现内部依赖 PlayerCameraManager，不先判空则可能在相机管理器尚未建立的瞬间崩溃；GetPlayerViewPoint(CamLoc, CamRot) 返回的是相机的世界位置与旋转而非 Pawn 的位置——相机可能带有弹簧臂滞后、震动或视角混合，判定必须建立在“玩家实际看到的视点”上，而非角色的逻辑坐标。

CamRot.Vector() 取旋转的前向单位向量；旋转中的 Roll 分量不影响前向向量，因此相机翻滚不会干扰视线判据。同一样本内，位置判据使用 CamLoc，视线判据使用 CamForward，二者来自同一次采样，保证两项判据考察的是同一瞬间的状态，不会出现位置与朝向错帧。

5.3 位置判据：方向与距离的联合约束

对每个碎片，代码计算两个偏差量，并要求二者同时落入容差：

代码 5-4 逐碎片的位置判据（节选自 `PerspectivePuzzleManager.cpp` 的 `CheckPuzzle()`）

	for (const auto& Point : CalibratedData)
	{
		FVector ToFragment = Point.WorldLocation - CamLoc;
		float CurrentDist = ToFragment.Size();
		FVector CurrentDir = ToFragment.GetSafeNormal();

		// 位置检测：相机到碎片的方向 / 距离 是否匹配标定值
		float Dot = FVector::DotProduct(CurrentDir, Point.TargetDirection);
		float DistDiff = FMath::Abs(CurrentDist - Point.TargetDistance);

		if (Dot >= DotProductThreshold && DistDiff <= DistanceTolerance)
		{
			PassCount++;
		}
		else
		{
			UE_LOG(LogTemp, Log, TEXT("  Mismatch: Dot=%.4f(need>=%.4f) DistDiff=%.1f(need<=%.1f)"),
				Dot, DotProductThreshold, DistDiff, DistanceTolerance);
		}
	}

两项判据的数学形式为：

Dot = ((P − C)/|P − C|) · d̂ ≥ DotProductThreshold

DistDiff = ||P − C| − TargetDistance| ≤ DistanceTolerance

其中 C 为相机位置，P 为碎片世界坐标，d̂ 为标定方向。由于 d̂ 与当前方向都是单位向量，Dot 即二者夹角的余弦 cos θ。由此可把阈值翻译成角度：默认值 DotProductThreshold = 0.996 对应约 5.13°，即工程表述中的"cos(5°)"；属性上的 ClampMin = 0.9 与 ClampMax = 1.0 把取值范围限制在 0° 到约 25.8° 之间。

表 5-1 方向阈值与角度容差的对应

DotProductThreshold对应角度语义
0.996（默认）约 5.1°“站得很准”的量级
0.900（ClampMin）约 25.8°参数允许的最松值

距离判据是绝对差而非相对误差：DistanceTolerance = 50 的含义是“相机到碎片的距离与标定距离相差不超过 50 个世界单位（厘米）”。绝对差有一个直接后果——同一个容差对不同距离的碎片严格程度并不相同：对 300 单位外的碎片，50 单位相当于约 17% 的相对误差；对 1500 单位外的碎片则只有约 3%。当场景中碎片的标定距离相差悬殊时，若需要等价的相对严格度，应把这一项改为按比例判定。

两项判据缺一不可：方向对“沿标定射线的前后位移”完全不敏感（沿该射线移动时 cos θ 恒为 1），只有距离项能约束它；而距离对“绕碎片球面的横向位移”不敏感，只有方向项能约束它（详见 4.3）。日志中“点积很高但距离差很大”与“距离差很小但点积很低”这两类条目，正对应两种单侧偏差。

5.4 通过率判据：允许个别碎片不达标

逐碎片比较的结果被汇总为一个通过比例，再与门限比较：

Rate = PassCount / CalibratedData.Num() ≥ RequiredPassRate

RequiredPassRate 默认 0.8，取值范围被限制在 0 到 1。它的工程意义是容忍个别碎片失配：碎片数量多时，总会有某个碎片因遮挡、贴花偏移或摆放误差而略微超标，若要求 100% 通过，谜题会变得脆弱且难以调优。但比例判据是离散的——通过率只能取 k/N 这些值，因此 0.8 的实际效果取决于碎片数量：

表 5-2 `RequiredPassRate = 0.8` 时实际需要的通过数

碎片数 N需要通过数 ⌈0.8N⌉允许失配数说明
220比例判据退化为“全部通过”
4400.75 已低于门限

这张表揭示了一个容易误判的点：在碎片数小于 5 的场景里，把 RequiredPassRate 设为 0.8 与设为 1.0 的效果完全相同，容错并未真正启用；若要获得“允许一半碎片失配”的语义，需把门限降到 0.5，但那样在两个碎片时就会退化为“只要一个碎片对上”，判定强度大幅下降。

5.5 视线判据：为什么位置判据单独不够

位置判据只依赖相机位置，与相机朝向无关。玩家站在正确位置、低头看着地面时，指向碎片的单位向量与标定值仍然一致，位置相关的两项判据照常通过。要排除这类姿势，必须额外引入朝向约束：

代码 5-5 视线判据（节选自 `PerspectivePuzzleManager.cpp` 的 `CheckPuzzle()`）

	// 朝向检测：玩家视线是否对准图案中心方向（独立于单个碎片）
	FVector ViewTargetDir = (CalibratedViewTarget - CalibratedOrigin).GetSafeNormal();
	float ViewDot = FVector::DotProduct(CamForward, ViewTargetDir);
	bool bViewMatch = (ViewDot >= ViewAngleThreshold);

其中参考方向由标定产物直接给出：

ViewTargetDir = normalize(CalibratedViewTarget − CalibratedOrigin)

ViewDot = CamForward · ViewTargetDir ≥ ViewAngleThreshold

ViewAngleThreshold 默认同样为 0.996，即约 5.1°。它回答“玩家是否正看着图案整体”，与位置判据回答的“玩家是否站在正确位置”正交。

为什么参考方向取图案中心而不是某个碎片。 碎片有两个以上时，从原点看向各个碎片的方向互不相同，而相机前向只能有一个方向；若要求视线同时对准每一个碎片，判据在数学上不可满足——除非这些碎片在屏幕上恰好重合，而那正是拼合成功的特例。取几何中心则给出唯一一个参考方向，并与“玩家在看完整图案”这一行为直接对应（几何中心的选取理由详见 4.4）。

有一点必须明确：ViewTargetDir 是标定阶段算出的固定方向，与相机的当前位置无关。因此视线判据单独并不构成位置约束——玩家站在任何地方，只要朝向恰好等于该方向，视线判据同样通过；反之，站在正确位置但朝向偏离超过约 5°，视线判据就会失败。两条判据必须取逻辑与，才同时约束“站在哪”与“朝哪看”。

5.6 联合判定、保持计时与完成

两条判据的结果被合并为一个瞬时布尔量，并进入计时状态机：

代码 5-6 联合判定与保持计时（节选自 `PerspectivePuzzleManager.cpp` 的 `CheckPuzzle()`）

	float Rate = (float)PassCount / (float)CalibratedData.Num();
	bool bAlignedNow = (Rate >= RequiredPassRate) && bViewMatch;

	// 调试：打印当前检测状态
	UE_LOG(LogTemp, Log, TEXT("CheckPuzzle: Pass=%d/%d Rate=%.2f ViewDot=%.4f Aligned=%s"),
		PassCount, CalibratedData.Num(), Rate, ViewDot, bAlignedNow ? TEXT("true") : TEXT("false"));

	if (bAlignedNow)
	{
		if (!bWasAligned) OnViewAligned();

		HoldTimer += DetectionInterval;
		SolveProgress = FMath::Clamp(HoldTimer / HoldDuration, 0.0f, 1.0f);
		OnProgressUpdated(SolveProgress);

		if (HoldTimer >= HoldDuration)
		{
			bIsSolved = true;
			SolveProgress = 1.0f;
			OnProgressUpdated(1.0f);
			OnPuzzleSolved();
			GetWorldTimerManager().ClearTimer(DetectionTimerHandle);
		}
	}
	else
	{
		if (bWasAligned) OnViewLost();
		HoldTimer = 0.0f;
		SolveProgress = 0.0f;
	}

判定链条可以概括为：

bAlignedNow = (Rate ≥ RequiredPassRate) ∧ bViewMatch

HoldTimer ← bAlignedNow ? HoldTimer + DetectionInterval : 0

SolveProgress = clamp(HoldTimer / HoldDuration, 0, 1)

几个关键语义：

  • 固定步长累加。 HoldTimer 每次增加的是 DetectionInterval 这一标称值，而不是回调的真实时间差。因此“保持时长”被量化为“连续对齐的检测周期数”：HoldDuration = 1.5、DetectionInterval = 0.1 时需要连续 15 个对齐周期。
  • 进度是归一化的保持量，不是“接近程度”。 SolveProgress 只反映对齐已经持续了多久，不反映站位的精确程度。HoldDuration 取非正值时，首个对齐周期即满足 HoldTimer >= HoldDuration，等价于“一对齐即解出”。
  • 失配立即清零。 未对齐的分支不做任何衰减，直接把 HoldTimer 与 SolveProgress 归零，因此保持窗口内不允许中断，谜题是“全有或全无”的；进度回退也因此是瞬时的，视觉上会出现跳变。
  • 完成即停止检测。 解出时把 bIsSolved 置真、SolveProgress 固定为 1.0、触发事件，最后清掉循环定时器；此后 CheckPuzzle 即便被调用，函数开头的守卫也会立刻返回。

5.9 小结与调参含义

检测系统的整体形态是：一个 10 Hz 的采样器 + 一组空间判据 + 一个保持计时器。空间判据由四层构成，每层排除一类错误姿势——方向判据排除“横向偏离”；距离判据排除“沿射线前后偏离”造成的视差错位；视线判据排除“位置正确但没看图案”（低头、转头）；通过率判据吸收个别碎片的噪声。四层之上，保持计时器排除“一晃而过”。任何一层被调松，都会重新引入它原本负责排除的那类姿势。

因此调参的正确顺序是：先看日志中“相机到标定原点的距离”（Offset），它应当趋近 0；再看逐碎片的 Dot 与 DistDiff 中哪一项超标。若 Offset 明显偏大，应先修正 CameraHeightOffset，而不是动阈值。只有当 Offset 已经很小、而 Dot 或 DistDiff 仍稳定略微超标时，才说明容差本身需要放宽——这时也应逐个参数调整并单独验证，避免多个参数同时改动后无法判断是哪一项生效。

边界与已知取舍： 检测基于单个玩家的相机且索引固定为 0；保持时长以检测周期为单位量化，最小分辨率等于 DetectionInterval；失配即清零，没有渐进回退；通过率是比例而非加权，所有碎片权重相同；距离容差是绝对量，其相对严格程度随碎片距离变化；解出后检测完全停止，同一 Manager 若要复用必须调用 ResetPuzzle()，若要改变基准还需重新 Calibrate()。

透视拼接谜题的视觉部分要解决两个问题：一张完整图案如何被拆成若干块并各自显示其中一部分，以及判定结果如何被玩家看见。前者决定碎片的表现形态，后者决定反馈是否可感知。

6.1 图案的几何拆分

图案的拆分不发生在图像层面，而发生在纹理坐标层面。所有碎片共用同一张源贴图，每个碎片只在自己的材质里声明“取这张贴图的哪一块矩形”，因此拆分块数变化时不需要重新导出任何图像资源。

纹理坐标空间是一个单位正方形，两个轴都取值于 [0, 1]。取子区域由一次仿射变换完成：

UVsample = UVtexcoord × Tiling + Offset

其中 Tiling 控制缩放（取多大一块），Offset 控制平移（从哪个位置开始取）。子区域在纹理空间中的覆盖范围为：

u ∈ [Offset.u, Offset.u + Tiling.u]，v ∈ [Offset.v, Offset.v + Tiling.v]

把图案上下二等分，就是保持横向完整、纵向压缩一半并施加纵向偏移：上半部分取 Tiling = (1, 0.5)、Offset = (0, 0)；下半部分取同样的 Tiling，但 Offset = (0, 0.5)，使取样窗口从纵向中点开始。

两个碎片的取样窗口互补且不重叠，合起来覆盖完整图案。由于采样窗口由材质参数给出，把图案拆成四块或九块时，只需要新增材质实例并填入对应的 Tiling 与 Offset，源贴图与节点网络都不必改动。

碎片在场景中的位置是另一个独立维度：它们被摆放在不同的纵深上，彼此之间存在视差。玩家横向移动时，近处碎片在视野中的位移大于远处碎片，两块因此错开；只有回到标定视点，两个取样窗口才在屏幕上重新拼合。拆分方案负责“每块显示什么”，纵深摆放负责“何时能拼合”，两者互不干涉。

6.2 材质侧的 UV 变换：节点结构与参数化

UV 变换在材质图中由三个节点完成：一个纹理坐标节点、一个乘法节点、一个加法节点。参数以向量形式接入，再经过通道裁剪后参与运算。

代码 6-1 UV 变换的节点连接（节选）

TexCoord ──▶ Multiply(A) ──▶ Add(A) ──▶ TextureSample.UVs
                 ▲              ▲
                 │(B)           │(B)
        UVTiling ─┴─ Mask(RG)   │
        UVOffset ───────────────┴─ Mask(RG)

链条的语义十分直接：先按 Tiling 缩放原始纹理坐标，再按 Offset 平移，结果送入纹理采样的坐标输入。节点顺序不可交换——先平移后缩放会得到 (UV + Offset) × Tiling，与目标式 UV × Tiling + Offset 不等价。

参数为什么用向量类型。 UVTiling 与 UVOffset 各自需要两个分量（u、v），声明为向量参数后，一组数值可以在细节面板上一次填完，且在材质实例中作为整体被覆盖。若改用两个标量参数，参数数量翻倍，实例侧需要维护的条目也随之翻倍。

为什么必须做通道裁剪。 向量参数的默认通道数是四（RGBA），而纹理坐标只有两个通道。UE 的算术节点要求两侧通道数一致，直接相连会在材质编译时得到类型错误：

代码 6-2 通道数不匹配时的编译诊断

SM6 (Node Multiply) Arithmetic between types float2 and float3 are undefined

这条报错的字面含义是“两个操作数的通道数不同，且不存在这样的算术定义”。它的成因有三种可能，需要逐个排查：一是向量参数本身是四通道；二是向量参数后接了通道裁剪节点，但裁剪后仍保留了三个通道（例如 B 通道未关闭），输出为 float3；三是未做裁剪而直接用四通道参数参与运算。把裁剪节点配置为只保留 R 与 G（B、A 均关闭）后，两侧都是 float2，运算即可成立。

该问题的排查路径值得说明：错误信息只给出节点名与两个类型，并不指出哪一侧“多余”。实际定位时，需要检查裁剪节点的通道勾选状态——它决定了输出通道数，而在细节面板中，多勾一个通道并不会立即报错，直到该节点的下游参与算术运算才暴露。

为什么在材质实例中调参，而不是修改材质本体。 母材质负责“有哪些参数、节点如何连接”，材质实例负责“这些参数取什么值”。两者分离带来三点收益：其一，一份母材质配多个实例即可表达任意数量的碎片，不需要复制节点网络；其二，实例只覆盖被显式勾选的参数，其余参数继续继承母材质，因此调整母材质中的公共逻辑会自动传播到全部实例；其三，实例是轻量资产，复制与改名不涉及图结构，新增一个碎片的表现成本接近于零。

6.3 承载方式的选择：贴画与网格体

碎片的载体在实现上并不唯一：可以是贴合表面的贴画组件（UDecalComponent），也可以是独立的网格体组件（UStaticMeshComponent，例如一块平板）。前者沿表面弯曲、天然贴合柱面与墙面；后者是一个独立几何体，位置与朝向完全自由，可用于悬浮碎片。

系统不要求所有碎片采用同一种载体，因此在初始化时按组件类型分支处理：

代码 6-3 材质缓存的承载分支与优先级（节选，末尾的日志输出已省略）

void APerspectivePuzzleManager::CacheFragmentMaterials()
{
    FragmentMaterials.Empty();

    for (AActor* Actor : FragmentActors)
    {
        UMaterialInstanceDynamic* DynMat = nullptr;

        if (UDecalComponent* Decal = Actor->FindComponentByClass<UDecalComponent>())
        {
            if (UMaterialInterface* DecalMat = Decal->GetDecalMaterial())
            {
                DynMat = UMaterialInstanceDynamic::Create(DecalMat, Decal);
                Decal->SetDecalMaterial(DynMat);
            }
        }
        else if (UStaticMeshComponent* SM = Actor->FindComponentByClass<UStaticMeshComponent>())
        {
            DynMat = SM->CreateAndSetMaterialInstanceDynamic(0);
        }

        FragmentMaterials.Add(DynMat);
    }
}

这段分支逻辑包含三层判定，每层都有明确的语义。

第一层是载体优先级。 FindComponentByClass0() 在 Actor 的组件集合中查找指定类型的组件，找不到时返回空指针。分支采用 if / else if 而非两个并列的 if，因此贴画优先于网格体：当一个 Actor 同时挂载了两种组件时，只有贴画会被处理，网格体分支不会执行。这一优先级与视觉语义一致——贴画是显式声明“此处用于贴合展示”的组件，而网格体是通用组件，可能仅作为碰撞体或占位体存在。

第二层是材质是否存在。 贴画分支内部还有一次判空：GetDecalMaterial() 在未指定材质时返回空指针。此处的处理方式是“不创建动态实例”，而不是中断或报错，使未配置材质的碎片被安静跳过。

第三层是空项容忍。 无论走哪个分支，DynMat 最后都会被压入 FragmentMaterials，即使它仍为空指针。这保证了 FragmentMaterials 与 FragmentActors 严格等长且按下标一一对应：索引 i 的材质项永远对应索引 i 的碎片。数组因此可以在需要时按索引关联回碎片，也避免了在下游用“跳过计数”的方式推算对应关系。空项由写入端容忍——发光循环在调用前检查指针是否为空。

6.4 动态材质实例

材质参数有两类存在形式：资产中保存的材质实例（含母材质）其参数值是静态的，作为资产数据被序列化；只有运行时创建的动态材质实例（UMaterialInstanceDynamic）才提供写入接口。使用 SetScalarParameterValue 之类的方法改变参数，前提是目标必须是动态实例，否则调用无从作用于渲染。

因此系统在初始化阶段一次性建立动态实例，并在整个运行期复用：

代码 6-4 动态实例的保存与后续写入（节选）

    //每个碎片对应的动态材质实例（用于控制发光） 
    UPROPERTY(Transient)
    TArray<UMaterialInstanceDynamic*> FragmentMaterials;

该数组被标记为 Transient，即不参与序列化：动态实例是运行时对象，没有必要写入存档，也不应在关卡加载时被反序列化。数组的元素类型为裸指针而非智能指针，其生命周期由组件侧的引用保证——每个实例在创建后立即被回写到对应的贴画或网格体组件上，组件持有引用即意味着实例不会被提前回收。

创建时机被安排在初始化阶段，而不是判定循环中。 判定循环以固定间隔反复执行，若在其中创建材质实例，每次采样都会产生一批新对象，既浪费内存也会失去“参数可在帧间累积”的前提——发光参数的写入依赖同一个实例被持续复用。把创建集中在 CacheFragmentMaterials() 中执行一次，后续只做写入，是整个发光链路能够平滑连续的前提。

两条创建路径的差异值得单独说明：

  • 网格体路径：CreateAndSetMaterialInstanceDynamic(0) 一步完成“创建实例并将它设置到第 0 个材质元素”。参数 0 表示材质元素索引，网格体可以有多个材质槽，此处固定使用第一个。
  • 贴画路径：先 GetDecalMaterial() 取得当前材质接口，再 UMaterialInstanceDynamic::Create(DecalMat, Decal) 以该材质为母本创建实例，第二个参数指定外层对象（Owner），最后 SetDecalMaterial(DynMat) 把实例回写到组件。若不执行最后一步，实例虽然存在却不会被渲染使用——这是该路径最容易遗漏的一环。

            if (DynMat) DynMat->SetScalarParameterValue(GlowParameterName, GlowValue);
        }
    }

参数名由 GlowParameterName 决定，默认值为 GlowIntensity。它被设计为可编辑属性，是为了让材质侧的命名不被 C++ 写死；而当该属性被置为空名（NAME_None）时，整段发光逻辑被跳过，系统退化为“无视觉反馈”的纯判定模式。

写入值 GlowValue 的取值规则是渐进语义：处于对齐状态时取当前进度 SolveProgress，否则取 0。进度本身由保持时长归一化而来（clamp(HoldTimer / HoldDuration, 0, 1)），因此发光强度与“玩家已经正确保持了多久”成正比；一旦失去对齐，SolveProgress 被清零，发光随之熄灭。玩家因此可以从亮度直接读出进度，而不必依赖额外 UI。

链条中两个常数各有明确职责。乘数 K 决定动态范围：参数从 0 变到 1 时，亮度在 1 与 1 + K 之间变化，取 K = 6 时对应 7 倍亮度；K 是纯调参量，效果不足时可增大到 15 或 30，链条结构不变。加数 1 则保证零点语义：参数为 0 时自发光等于贴图原色，图案保持正常外观，而不是完全熄灭。若省略该偏置，未对齐状态下图案会变成全黑。

发光接自发光通道而不是基础色，是这条链路的关键选择。 基础色参与光照着色计算，提高基础色只会让图案“更亮更白”，颜色被稀释，观感是漂洗而非发光；自发光则是直接叠加到最终亮度的独立项，提高它不会改变图案的色相，只是让同一颜色变得更耀眼，观感与光源一致。

自发光之外还需要一道后处理才能形成“光晕”：自发光本身只提供亮度，扩散感来自泛光（Bloom）。实现方式是在场景中放置一个后处理体积并勾选无限范围（Unbound），将 Bloom Intensity 调到约 1.5 ~ 3。缺少这一步时，图案会“变亮”但不会“发光”——这是发光反馈在观感上不达预期时首要检查的环节。

6.6 视觉方案的取舍

实现“碎片拼合后发光”至少有三条技术路线，它们在可控性、实现成本与最终效果上各有取舍。

其代价也很明确：贴画路线的材质域被限定为 Deferred Decal，混合模式与可用的着色模型都受到约束，图案的最终观感受表面法线与投影方向影响；网格体路线虽无此约束，却失去了“自动贴合表面”的能力，需要人工把平面摆到与目标表面几乎重合的位置。

6.7 小结

  • 图案拆分在纹理坐标层面完成：所有碎片共用一张源贴图，每个碎片用一组 Tiling 与 Offset 声明取样窗口，拆分块数变化时不需要重新制作图像资源。
  • 材质侧的 UV 变换是“先缩放、后平移”的两步链条，顺序不可交换；参数以向量形式声明后再裁剪为双通道，否则会因通道数不一致触发 float2 与 float3 不可运算的编译错误。
  • 参数值放在材质实例而非母材质中：母材质定义参数与拓扑，实例只覆盖数值，新增碎片因此只需复制实例。
  • 碎片载体在贴画与网格体之间分支处理，if / else if 的顺序使贴画具有优先级；材质数组与碎片列表严格等长同序，空项由写入端容忍，因此单个碎片配置缺失不会破坏索引关系。
  • 动态材质实例在初始化阶段一次性创建并持续复用，是运行时可写参数的前提；贴画路线需要“取材质、创建实例、回写组件”三步，缺一不可。
  • 发光通过单个标量参数驱动自发光通道，参数值取“对齐时按进度、失焦时归零”，并配合泛光形成光晕；接到基础色只会造成颜色漂洗，不产生发光观感。

7.1 UE 的构建系统与 UHT：反射代码是怎样生成的

一个 UE C++ 类与普通 C++ 类最直观的差别，是头文件里那两样东西：末尾的 #include "PerspectivePuzzleManager.generated.h"，以及类体第一行的 GENERATED_BODY()。它们不是可选风格，而是反射系统能够识别这个类的前提。

UE 的 C++ 构建分为两层。第一层是 UHT（Unreal Header Tool），它不编译代码，而是扫描头文件中出现的 UCLASS、USTRUCT、UPROPERTY、UFUNCTION 等标记，据此生成若干辅助文件，其中最主要的就是 0.generated.h。第二层是 UBT（Unreal Build Tool） 调用平台编译器（本工程为 MSVC），把头文件、生成文件与源文件一起编译成模块动态库，由引擎在启动时加载。整个顺序如图 7-1 所示。

python -c "p='F:/ue5_project/CPP1/Source/CPP1/Public/PerspectivePuzzleManager.h'; raw=open(p,'rb').read(); b=b'\xef\xbb\xbf'; print('BOM count =', 2 if raw.startswith(b+b) else 1 if raw.startswith(b) else 0)"

7.5 定时器与生命周期

检测逻辑没有放在 Tick 中。构造函数把 PrimaryActorTick.bCanEverTick 设为 false，时间基准完全交给定时器：检测按固定间隔触发，而不是每帧触发。

代码 7-3 构造、BeginPlay 与 ResetPuzzle（节选自 PerspectivePuzzleManager.cpp 第 14–28、103–112 行）

APerspectivePuzzleManager::APerspectivePuzzleManager()

{
	Super::BeginPlay();

{
	bIsSolved = false;
	bWasAligned = false;
	HoldTimer = 0.0f;
	SolveProgress = 0.0f;

}

四点在工程上值得注意：

  1. BeginPlay 的调用顺序有依赖关系。 Calibrate() 先建立标定数据，CacheFragmentMaterials() 再为每个碎片创建动态材质实例，最后 ResetPuzzle() 启动定时器；若先启动定时器，第一次检测会在标定数据为空时执行，虽然 CheckPuzzle 有 CalibratedData.Num() == 0 的提前返回作为兜底，但那属于防御性写法而非常规路径。
  2. FTimerHandle 是定时器的句柄，不是定时器本身。 SetTimer 把定时器登记到世界（UWorld）的定时器管理器上，句柄只是访问它的凭据。因此 ClearTimer(DetectionTimerHandle) 是「取消这个句柄登记的那个定时器」，而 SetTimer 的第五个参数为 true 表示按 DetectionInterval 反复触发，而不是只触发一次。
  3. ResetPuzzle 是先清后设。 它既用于初始化，也用于求解后的重新开始：先 ClearTimer 取消可能存在的旧定时器，再 SetTimer 重新登记，这样重复调用不会叠加出多个定时器。
  4. 求解后停止检测有两条保障。 一是 CheckPuzzle 开头的 if (bIsSolved || CalibratedData.Num() == 0) return;，二是 bIsSolved = true 之后立即 ClearTimer。前者保证即使定时器仍存在也不会继续运算，后者则彻底释放定时器。

还有一处与「保持时长」语义相关：持续时间由 HoldTimer += DetectionInterval 累加，而不是累加实测帧间隔。这意味着 HoldDuration 是以「检测次数 × 名义间隔」度量的；当「定时器的实际触发周期」与 DetectionInterval 不一致（例如帧率极低导致定时器被推迟）时，实际保持时长会与设定值有偏差。若需要严格的时间语义，应改为累加实测时间或使用时间戳差值。在头文件默认值 DetectionInterval = 0.1、HoldDuration = 1.5 下，约 15 次连续检测即视为保持成功；若按附录 A.2 的参考取值把 HoldDuration 调整为 2.0 秒，则需要约 20 次。

日志语句的关键在于把阈值与实测值一起打印。例如碎片未通过时输出的格式串为：

			UE_LOG(LogTemp, Log, TEXT("  Mismatch: Dot=%.4f(need>=%.4f) DistDiff=%.1f(need<=%.1f)"),
				Dot, DotProductThreshold, DistDiff, DistanceTolerance);

该行同时给出实测的方向点积、要求的阈值、实测的距离差与允许的容差，因此不需要额外推算即可判断应当放宽哪一项参数。同理，汇总行同时给出通过数量、总数、通过率与视线点积，可以直接区分「碎片数量多导致通过率不足」与「视线方向不满足」这两种失败原因。

调试绘制中的 Duration 参数表示图形在场景中保留的秒数。工程在一处用了两个极端的取值，二者的用途不同：

  • BeginPlay() 中的 DrawDebugCalibration(100000.0f) 传入一个极大的时长，使标定球体与连线在整个运行期内持续可见，作为常驻的参照物；
  • CheckPuzzle() 中的视线线段传入 DetectionInterval * 2.0f，即约为两个检测周期。线段每周期被重绘一次，因此视觉上连续，同时避免了大量图形对象长期堆积。

需要注意的是，调试绘制只在开发构建中可用：打包后的运行版本不会绘制这些图形，因此它们适合作为定位手段，而不能作为面向玩家的反馈——面向玩家的反馈应通过材质发光参数与蓝图事件实现。

DrawDebugCalibration 声明为 const 成员函数，表示它不修改对象状态；对只读的调试函数而言，这类限定同时是给调用方的保证。语言层面还有一类与之互补的契约表达：C++17 的 [[nodiscard]] 属性要求调用方必须使用返回值，否则编译器给出告警。本工程的对外接口以 void 函数与蓝图事件为主，未使用该属性；当某个查询函数返回值本身具有语义（例如「当前是否处于对齐状态」）时，该属性是把调用约定写进类型系统的常用手段，而「按常量引用传递只读参数」则是对应的参数侧写法。

7.7 小结

  1. 反射代码由 UHT 生成，生成失败会伪装成满屏语法错误。 .generated.h 与 GENERATED_BODY() 是反射的前提；排查时应先确认生成阶段是否成功，再阅读模板与语法报错。
  2. 头文件承载声明与反射标记，源文件承载实现与引擎依赖。 生成头文件置于所有 include 之后、源文件首条 include 为自身头文件，这两条约定共同保证宏展开顺序稳定。
  3. 模板静态断言报错通常指向一个不完整类型。 E0842 / E0094 出现在引擎头文件中时，应回头检查容器元素的书写方式（如 TObjectPtr0 与前向声明类型组合），而不是修改引擎侧代码。
  4. 编码约定必须全工程统一。 带 BOM 与不带 BOM 两条路线各自成立，混用会产生局部乱码；双重 BOM 会直接破坏 UHT 解析。
  5. 定时器使检测频率与帧率解耦，但也带来时间语义上的近似。 SetTimer 的循环触发配合 bIsSolved 提前返回与求解后 ClearTimer，构成了停止检测的双重保障；而保持时长按名义间隔累加，是需要知晓的实现细节。
  6. 可用的调试手段应把「阈值」与「实测值」一并暴露。 这样一条日志就能回答「哪条判据没通过、差多少」，避免在参数面板中反复试错。

8.3 两类失效模式与参数取舍

失效模式一：无法触发。 表现为玩家自认为已站在正确位置，进度条却始终为零。其机制是至少一个判据未达标，常见来源有三：

  • 相机高度与标定原点不匹配：角色相机高度随姿态（站立、下蹲）变化，而标定原点在场景中固定；
  • 碎片在标定之后被移动，标定数据失效；
  • 容差过严：DistanceTolerance 偏小或 DotProductThreshold 偏高。

失效模式二：误触发。 表现为玩家站在明显不正确的位置也能触发，或触发时图案并未真正拼合。其机制是判据过于宽松，常见来源有二：

  • RequiredPassRate 过低，少量碎片达标即通过；
  • 缺少朝向约束：仅用位置判据时，玩家在正确位置附近转身仍可触发。

两类失效模式是同一组参数的两端。工程做法是先固定 HoldDuration 与 DetectionInterval，再依次收紧方向阈值、距离容差与通过率，每步都用调试可视化确认判定边界与预期一致。

8.4 调试手段

系统内置两类互补的调试输出。

8.5 标定一致性验证流程

标定数据是运行期判定的唯一依据，其正确性只能通过「站在标定位置看是否达标」来验证。建议流程如下：

  1. 完成碎片摆放，确认各碎片位于不同的纵深位置；
  2. 触发一次标定，检查日志中的记录条数与碎片数量一致；
  3. 打开调试可视化，确认青色球体位于预期高度（管理器位置加相机高度偏移），橙色球体与碎片一一对应；
  4. 将相机移动到标定点，观察两条调试射线是否重合、通过率是否为 1.0、朝向点积是否接近 1.0；
  5. 若通过率不足 1.0，按日志逐条修正碎片位置或容差；
  6. 保持正确视角超过保持时间，确认事件被触发、进度走满、碎片发光归一。

移动任一碎片后必须重新标定：TargetDirection 与 TargetDistance 均以标定原点为参考计算，碎片移动即失效。

8.6 性能与数值考量

  • 计算量：每次检测对 N 个碎片各做一次向量减法、取模、归一化与点积，复杂度 O(N)；默认 0.1 秒的周期使该开销与帧率解耦，并与 N 呈线性关系。
  • 使用余弦而非角度：避免反三角函数，同时避免浮点相等比较。
  • 比较使用下界：方向判据为「点积 ≥ 阈值」，距离判据为「偏差 ≤ 容差」，边界值即通过，语义清晰。
  • 归一化的安全处理：向量归一化使用 GetSafeNormal()，在向量长度为零时返回零向量而不产生 NaN。
  • 定时器与状态：检测在定时器回调中执行，bIsSolved 为真时提前返回并清除定时器，避免解谜完成后继续计算。

8.7 小结

参数标定的本质是在「宁可触发不了」与「宁可误触发」之间选择工作点：前者牺牲手感，后者牺牲谜题的可信度。可行做法是先按默认值运行、用可视化确认几何关系无误，再依据失效模式的类型定向调整单一参数，并在每次调整后重复 8.5 的验证流程。

#9结论

9.1 主要结论

  1. 视角判定必须同时约束位置与朝向，二者不可互相替代。 位置判据（相机到各碎片的方向与距离）保证玩家站在能让碎片在几何上拼合的位置；朝向判据（相机朝向与图案中心方向的一致性）保证玩家正对图案。缺少后者时，玩家在正确位置转身即可触发，谜题的可信度随之丧失。
  1. 把「正确视角」表示为相对量（方向 + 距离）比表示为绝对坐标更利于工程实现。 方向与距离以标定原点为参考，与场景的绝对坐标系无关；移动整个谜题后只需重新标定一次，判定逻辑无需修改。
  1. 阈值以余弦形式表达兼顾了计算成本与操作手感。 点积的结果本身就是余弦，无需反三角函数；余弦在接近 0° 处变化平缓，使容差随视角接近正确而自然放宽，默认 0.996 对应约 5°。
  1. 连续量经「通过率 + 保持时间」转换为事件，可有效抑制抖动。 单次检测的瞬时波动不会触发谜题，只有持续满足条件达到保持时间才判定解开；同时进度量被保留下来驱动视觉反馈。
  1. 检测与呈现应通过参数解耦。 检测层只输出 [0, 1] 的进度值，呈现层通过材质标量参数消费它；更换图案或更换承载方式（贴画、网格体）不影响检测逻辑。
  1. 引擎反射系统对头文件结构有硬性约束，多数「诡异」的编译错误源于约束被破坏。 生成头文件的包含位置、宏的顺序、构建产物是否重新生成，都会以看似无关的模板报错形式出现。

9.2 工程实践清单

  • 碎片必须在纵深上分开摆放；若两个碎片位于同一深度，视差为零，谜题在多个位置都可能成立。
  • 标定原点取相机高度而非管理器本体高度，避免每次标定都要手动抬高管理器。
  • 标定之后移动碎片必须重新标定；建议把标定与调试绘制绑定为可重复调用的操作。
  • 调参顺序固定为：先确认几何关系（可视化）→ 再放宽容差使判定能够触发 → 最后逐步收紧直至手感合适。
  • 调试时优先看日志中的三项偏差（方向点积、距离偏差、朝向点积），它们直接对应三条判据。
  • 面向玩家的反馈应从「对齐即满值」改为「随进度连续变化」，以降低保持过程的枯燥感。

9.3 局限

  • 不检测遮挡。 判据只比较方向与距离，若某个碎片被中间物体遮挡，系统仍会判定对齐。覆盖该情形需要额外的射线检测，并付出与碎片数量成正比的射线开销。
  • 未考虑相机参数变化。 判定依赖相机位置与朝向；若使用过肩视角、镜头抖动或动态视野，需要把相机位置替换为对应的观察点，并对抖动做时间平滑。
  • 单实例假设。 当前设计以一个管理器对应一个谜题；场景中存在多个谜题时需要多个实例，标定数据与状态彼此独立。
  • 不支持多阶段谜题。 状态机只有「未解开 / 保持中 / 已解开」三种状态；若谜题需要按顺序对齐多个视角，需要扩展状态表示。
  • 性能随碎片数量线性增长。 对常见规模（数个到数十个碎片）开销可忽略，但不适用于碎片数量极大的场景。

9.4 后续工作

  • 增加遮挡检测：对每个碎片做一次朝向碎片的射线检测，命中非碎片物体即判定该碎片不通过；
  • 把标定数据外置为可保存的资产，使标定结果可版本化与复用，而不依赖运行时重新标定；
  • 将判定逻辑与相机来源解耦，支持不同相机模式与观战视角；
  • 为判据补充自动化测试：构造若干已知位置与朝向的用例，验证通过率与事件触发是否符合预期；
  • 扩展到多视角谜题：以「视角集合 + 每个视角的碎片子集」描述谜题，检测当前视角属于集合中的哪一个。

C.1 从空工程到可运行谜题

  1. 创建 C++ 工程。 在引擎启动器中以「游戏 → 空白」模板创建 C++ 工程，工程名 CPP1，路径不包含中文与空格。确认使用的引擎版本为 5.8。
  2. 新建管理类。 在编辑器的 C++ 类向导中以 AActor 为父类创建 PerspectivePuzzleManager，生成头文件与源文件。
  3. 写入实现。 按 Source/CPP1/Public/PerspectivePuzzleManager.h 与对应源文件的内容写入声明与实现；两个文件均以「UTF-8 with BOM」保存。
  4. 首次构建。 关闭 Live Coding 或以补丁编译方式构建，确认构建成功、编辑器正常加载模块。此步若失败，按附录 B 的 B-1 至 B-5 排查，不要进入下一步。

  6. 建立母材质。 新建材质 M_BStar，设为不受光照（Unlit）与半透明 Decal 混合模式。取样链为：纹理坐标 → 乘以向量参数 UVTiling → 加上向量参数 UVOffset → 贴图的 UV 输入。发光链为：标量参数 GlowIntensity → 乘以固定倍数 → 加 1 → 乘以贴图颜色 → 自发光颜色输入。两条链路的参数都要在母材质中声明。
  7. 建立材质实例。 复制母材质得到两个实例：上半部分取 UVTiling = (1, 0.5)、UVOffset = (0, 0)；下半部分取 UVTiling = (1, 0.5)、UVOffset = (0, 0.5)。
  8. 摆放碎片。 在关卡中放置两个 Decal 组件，分别指定两个材质实例，调整其大小与位置使图案只覆盖目标表面。一个放在较近的柱子上，一个放在较远的墙面上，形成深度差——深度差是视差成立的前提。
  9. 放置管理器。 把 PerspectivePuzzleManager 拖入关卡，位置放在预期站立点的地面处。
  10. 登记碎片。 在管理器的细节面板中，把两个 Decal Actor 依次加入 FragmentActors 数组。
  11. 创建管理器蓝图。 以 C++ 类为父类创建蓝图 BP_PuzzleManager，在其中实现四个蓝图事件：OnPuzzleSolved（打印提示并触发开门等表现）、OnViewAligned、OnViewLost、OnProgressUpdated（可接进度条或音效）。C++ 侧只负责调用，表现层全部放在蓝图。
  12. 标定。 用调试绘制确认标定原点与碎片位置：运行后 BeginPlay 会自动标定并调用 DrawDebugCalibration；也可在编辑器细节面板点击对应按钮手动触发。调整 CameraHeightOffset，使其等于玩家相机在该站立点的高度。
  13. 调参。 按附录 A.2 的顺序调整检测参数：先 CameraHeightOffset，再 DotProductThreshold 与 DistanceTolerance，然后 RequiredPassRate 与 HoldDuration，ViewAngleThreshold 最后动。每次只改一个参数并立即验证。
  14. 配置光晕。 在关卡中放置后期处理体积并勾选「无边界」，把泛光强度设为 1.5–3；否则自发光只表现为图案变亮，没有扩散的光晕。
  15. 验证检测链路。 运行并观察输出日志：相机位置与标定位置的距离、逐碎片的 Dot 与 DistDiff、以及 Pass/Num/Rate/ViewDot/Aligned 汇总行。当站位正确而某项不通过时，该行会直接给出实测值与阈值之差。
  16. 验证反馈与事件。 站到标定位并朝向图案：碎片发光应随进度由暗到亮；移开视线或离开位置时发光归零；持续保持达到 HoldDuration 后触发 OnPuzzleSolved，蓝图侧的表现（提示、开门动画等）随之执行。
  17. 留存可复现配置。 把最终的参数取值、材质实例的 UV 取值、Decal 的尺寸与变换汇总成表，便于在其他关卡复用同一套材质与逻辑。
